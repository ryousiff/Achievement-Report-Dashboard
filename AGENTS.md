# Project Commands

- `npm run dev` starts the local dashboard.
- `npm run typecheck` validates TypeScript.
- `npm run build` creates the production build.
- `npm run test` runs the Vitest suite.
- `docker compose up -d` starts local PostgreSQL and MinIO after production passwords are replaced.

# Multi-Platform Connector Setup

Connectors live in `src/lib/connectors/`. The shared `SocialConnector` interface in `src/lib/connectors/types.ts` defines authorization, account discovery, callback persistence, and sync.

## Supported providers

- **Meta** (`meta`) — Facebook Pages + Instagram Business. Configure `META_APP_ID`, `META_APP_SECRET`, `META_REDIRECT_URI`, and `META_TOKEN_ENCRYPTION_KEY`.
  - `META_LOGIN_CONFIG_ID` (optional): a Facebook Login for Business configuration ID, for onboarding **external** client businesses only. Meta blocks selecting your own app's Business Portfolio as the client business in a Login Configuration — a business can't use Login for Business to grant access to itself. The orange "ربط ملف Meta جديد" OAuth button only appears when `META_LOGIN_CONFIG_ID` is configured; otherwise the UI directs admins to the system-user token flow.
  - For Kaan Creative's **own** Pages/Instagram accounts (owned by the same Business Portfolio that owns this app), use the admin-only system-user token flow instead: `POST /api/connectors/meta/system-user` (`connect_meta_system_user` feature, ADMIN only; UI panel on the Accounts page). An admin generates a non-expiring System User access token in Business Settings and pastes it in; the token is validated via `debugMetaToken`/`validateMetaSystemUserToken` (must be valid, issued for this app, non-expiring, and hold `pages_show_list`/`pages_read_engagement`/`instagram_basic`/`instagram_manage_insights`) and never persisted, logged, or returned — only `maskMetaToken`'s short preview is ever shown. Pages/Instagram accounts are discovered via the Business Manager API (`fetchBusinessManagedPages`, `owned_pages` + `client_pages`) using `META_BUSINESS_ID`, not `/me/accounts`. Shared/partner assets that can't be accessed are reported as warnings with statuses like `PARTNER_ACCESS_INSUFFICIENT` instead of aborting the whole discovery. Each Page's own access token is then encrypted (`encryptToken`) and stored per `MetaAccount`, same as the OAuth flow. Ad accounts (`fetchBusinessAdAccounts`) are discovered for assignment via `Client.metaAdAccountId`. Paid metrics are synced by `syncMissingClientAdMonth` in `src/lib/ads-insights.ts`; a shared ad account must be scoped to each client's own assets, never attributed wholesale to one client. Use `DELETE /api/connectors/meta/system-user` to revoke the local connection.
- **TikTok** (`tiktok`) — stub connector. Configure `TIKTOK_CLIENT_KEY`, `TIKTOK_CLIENT_SECRET`, `TIKTOK_REDIRECT_URI`. OAuth: `/api/connectors/tiktok`, callback: `/api/connectors/tiktok/callback`.
- **LinkedIn** (`linkedin`) — stub connector. Configure `LINKEDIN_CLIENT_ID`, `LINKEDIN_CLIENT_SECRET`, `LINKEDIN_REDIRECT_URI`. OAuth: `/api/connectors/linkedin`, callback: `/api/connectors/linkedin/callback`.
- **YouTube** (`youtube`) — stub connector. Configure `YOUTUBE_CLIENT_ID`, `YOUTUBE_CLIENT_SECRET`, `YOUTUBE_REDIRECT_URI`. OAuth: `/api/connectors/youtube`, callback: `/api/connectors/youtube/callback`.
- **X** (`x`) — stub connector. Configure `X_CLIENT_ID`, `X_CLIENT_SECRET`, `X_REDIRECT_URI`. OAuth: `/api/connectors/x`, callback: `/api/connectors/x/callback`.

A provider only exposes a working **Connect** flow when it is both `isConfigured()` (credentials present) and `isImplemented === true`. Stubs return a clear `not_implemented` error and are safe to leave configured.

## Adding a new connector

1. Implement the `SocialConnector` interface in `src/lib/connectors/<provider>.ts`.
2. Register it in `src/lib/connectors/registry.ts`.
3. If it supports sync, the worker will pick it up automatically via `getConnectorForPlatform()`.
4. Add the required environment keys to `.env.example` and `src/lib/env.ts`.

# Paid ads correctness and verification

- Verify Meta field names against the API version in `src/lib/meta-sync.ts`. For v23 creatives, request `instagram_user_id`, not the deprecated `instagram_actor_id`. Old boosted posts may not be in the synced media library; match explicit client identities and exclude other clients. Collaborative-media membership alone does not prove ad ownership.
- Never interpret permission errors, unresolved ownership, or incomplete pagination as a verified empty month. Log only safe error codes and client IDs, never access tokens or request URLs containing tokens. The sponsored-ads API exposes `autoStatus` separately from its HTTP status.
- Paid snapshots require the current scope version plus account/client-asset provenance. Reject older account-level totals. Refresh via atomic upserts, not deletion. Approved reports remain frozen; refresh/export stay database-only.
- Store original ad spend and billing currency. Capture approximate BHD conversions with the paid snapshot. Use USD pegs for pegged currencies and cached, dated ExchangeRate-API reference rates for others, with attribution. Missing rates must stay unavailable, never default to BHD or fabricated exchange rates. Historical conversions use the capture-time reference rate, not a historical settlement rate.
- `ad_reach` is currently a sum across owned ads and must be labelled non-unique. Impressions are not video views; messaging conversations started are not messages sent. Do not add overlapping action aliases together.
- Client budget totals combine automatic and manual ads in BHD; a manual row linked by `metaAdId` takes precedence over the automatic twin. Never publish a zero/partial total when fetching or conversion failed.
- Reproduce changes with regression tests before fixes: shared-account isolation, old boosts without a local post, per-object errors, currencies, linked manual deduplication, stale snapshot rejection, and readiness warnings. Passing unrelated legacy tests is not proof that a new integration works. Do not infer paid/organic breakdowns from unexplained screenshot icons or assume non-followers are paid delivery.
- `npm run test -- --silent --reporter=dot` runs the full suite with concise output. Also run `npm run typecheck` and `npm run build`. Tests involving month finalization must freeze time explicitly rather than depending on today's date.
- After schema-changing deployments, run `docker compose exec web npx prisma migrate deploy`; a missing column can make client queries fail without deleting any client data. Never recommend a destructive restore or deleting snapshots before checking the actual error.

# Sync scheduling

- `npm run worker` (also started alongside `npm run dev`) drains queued `SyncJob`s **and** periodically checks whether the daily automatic sync is due, via `runDueDailyClientSync()` in `src/lib/sync-queue.ts`. When due, it calls `enqueueClientSync()` for every active client — a normal incremental sync (`INCREMENTAL_MEDIA_SYNC` / `DAILY_ACCOUNT_INSIGHT_SYNC`), never the deep historical backfill.
- The due-check interval and the sync interval are configurable via `DAILY_CLIENT_SYNC_CHECK_INTERVAL_MS` (default 1h) and `DAILY_CLIENT_SYNC_INTERVAL_MS` (default 24h); see `getSchedulerConfig()` in `src/lib/env.ts`.
- The daily trigger is guarded by an atomic claim on the `Setting` table (`moduleId: "scheduler"`), so a worker restart or running multiple worker instances can't double-trigger it.
- **Historical Sync** (`POST /api/clients/:clientId/backfill`, `run_historical_sync` feature, admin-only) stays a separate, explicit, manual action for the initial deep backfill (15 months by default), recovering a partially-failed backfill, or re-syncing an older period — it is never triggered by the scheduler.
- **Thumbnail backfill**: `runDueThumbnailBackfill()` periodically (`THUMBNAIL_BACKFILL_CHECK_INTERVAL_MS`, default 10min) scans every Instagram connection for `SocialPost` rows still missing a permanently-stored thumbnail (`thumbnailStorageKey`, see `src/lib/media-storage.ts`) and enqueues one low-priority `THUMBNAIL_BACKFILL` job per connection that needs it — no manual per-client command required. Each job (`src/lib/media-backfill.ts`) only processes a small batch (`THUMBNAIL_BACKFILL_BATCH_SIZE`, default 15 posts), re-fetching a fresh `media_url`/`thumbnail_url` from Meta since the one already stored may have expired, then re-enqueues itself with a delay (`THUMBNAIL_BACKFILL_CONTINUATION_DELAY_MS`, default 5min) if posts remain — it never bursts through the whole backlog at once. It shares the exact same Meta app-wide cooldown as every other Instagram job (checked before claiming, activated on `(#4) Application request limit reached`), so it automatically pauses and resumes without starving normal account-insight/media sync. New posts already cache their thumbnail during normal `upsertPost()`; this backfill only ever catches up old posts synced before that existed. `scripts/backfill-media-thumbnails.ts` remains available as a manual debugging/repair tool but normal operation no longer depends on running it.
- **Post-level historical metric snapshots**: `SocialPost.metrics` is the *current/live* state and keeps changing whenever `runRecentInsightRefresh` re-syncs a post (for up to `RECENT_POST_REFRESH_DAYS`, default 60 days after publish) — summing it directly for an already-completed month causes report totals (organic views, likes, comments, saved, shares, total interactions, top posts) to silently drift upward every time the report is refreshed. `src/lib/post-metric-snapshots.ts` fixes this: every `upsertPost()` call also upserts an immutable `SocialPostMetricSnapshot` for the calendar month the post was published in. While that month is still open, the snapshot keeps tracking the live metrics; the first write observed after the month has fully elapsed finalizes it (sets `finalizedAt`) and it is never touched again. `reportPosts()`/`buildStandardReportBlocks()` (used by report create/refresh/export) resolve each post's metrics as LIVE (open month), SNAPSHOT (finalized + captured), or — only for periods that predate this feature and have no captured snapshot — a flagged `LIFETIME_FALLBACK`; `refreshReportData()` never lets a `LIFETIME_FALLBACK` result silently overwrite an already-saved KPI value or top-posts ranking. Account-level TOTAL_VALUE snapshots (reach, total views, followers gained/lost) are a separate, already-correct system and are untouched by this. Live media-library screens (the report builder's post picker, sponsored ads' post picker) intentionally keep reading `SocialPost.metrics` directly.
